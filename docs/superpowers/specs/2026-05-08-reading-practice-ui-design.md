# Reading Practice UI Design

**Date:** 2026-05-08  
**Status:** Approved

## Problem

The current reading-training flow is prompt-first and terminal-first. It can generate material and explain answers, but it does not provide a browser-based answering experience for users who want to read a passage, enter answers, submit once, and immediately see a structured review with both raw score and estimated IELTS Band.

## Proposed Solution

Add a local browser UI for reading practice that supports one complete first-version flow:

1. generate one original reading set from this repository
2. open a browser-based practice page
3. let the user answer and submit
4. show a review page with score and explanations
5. persist the attempt in the project locally

The first version is intentionally narrow. It only supports repository-generated original reading sets and optimizes for stable execution of the practice-to-review loop.

The browser UI is a delivery surface for the reading workflow. It must follow the existing `ielts-reading` skill contract rather than inventing a parallel training flow.

The `ielts-reading` skill itself must be updated so it can route eligible reading-practice requests into this UI flow.

## Scope

**In:** browser practice UI, browser review UI, raw score, IELTS Band estimate, local persistence, original reading sets generated by this repository, direct transition from submit to review, `ielts-reading` skill routing into the UI flow, CLI fallback when the UI cannot be used.  
**Out:** dashboard, cloud sync, account system, multi-user support, external passage import, complex mobile polish, draft autosave, advanced passage highlighting, UI support for user-pasted external passages in the first version.

## Architecture

### Core Units

| Unit | Responsibility |
|------|----------------|
| Reading Skill Router | Detect when a request should enter UI-based training instead of staying in the terminal |
| Shared UI Shell | Provide a consistent layout frame, typography, spacing, controls, and status styling for all reading-training sessions |
| Reading Set Generator | Produce one original passage, questions, answer key, evidence, paraphrase pairs, and explanations |
| Session Store | Persist generated set, submitted answers, and derived results in the project locally |
| Practice UI | Render the passage and questions, capture answers, and submit one completed attempt |
| Result Deriver | Compare submitted answers to the answer key and calculate score outputs |
| Review UI | Render raw score, IELTS Band estimate, and per-question review details |

### Reading Skill Alignment

The UI must execute reading training according to the current `ielts-reading` skill requirements.

That means the browser flow must preserve these rules:

- the training content is reading-focused, not a generic quiz shell
- question types and explanations follow the reading skill's analysis model
- answer key and detailed explanation are withheld before submission
- after submission, review content must support the same reasoning surfaces the skill expects:
  - correct answer
  - evidence sentence
  - paraphrase pairs
  - explanation of why the answer is correct or wrong
- future UI changes must be treated as extensions of the reading skill workflow, not replacements for it

### Skill Routing Rules

The first version must update `ielts-reading` so it can decide whether to use the browser UI.

Routing rules:

1. If the user intent is to **generate one repository-originated reading set and do the questions**, the skill should prefer the browser UI.
2. If the runtime environment does not support launching the UI, the skill should fall back to the existing CLI-style reading flow instead of failing.
3. If the user provides an external passage or asks for analysis of an existing set, the first version should stay in the current terminal-based reading workflow.
4. The skill should not ask an extra "Do you want UI?" question in the happy path; UI is the default for this supported training mode.

### UI Consistency Rule

UI style consistency is a first-version requirement, not a nice-to-have.

Every reading-training session launched by `ielts-reading` into the browser must reuse the same:

- page shell
- layout system
- typography scale
- spacing scale
- input styles
- button styles
- correctness / error / unanswered status colors

The implementation must not generate ad-hoc one-off screens with different styling per run. The UI may render different content per reading set, but the visual system must remain consistent across launches.

The visual system must be persisted in the project as implementation assets, not reconstructed only at runtime from prompts or transient state.

### Product Flow

The first version uses exactly two browser views:

1. **Practice Page**
   - title and set metadata
   - passage
   - question list
   - per-question answer controls
   - submit action
2. **Review Page**
   - raw score
   - estimated IELTS Band
   - correct answers
   - evidence sentences
   - paraphrase pairs
   - per-question explanation

No landing page or dashboard is required for the first version.

## Practice Page Design

The practice page uses a two-column layout:

- **Left / primary column:** reading passage
- **Right / secondary column:** questions and answer controls

The question column should remain independently scrollable so the user can answer without losing their position in the passage.

This layout should come from the shared UI shell rather than being redefined separately for each generated training session.

### Input Controls

- **True/False/Not Given:** single-choice controls
- **Sentence Completion:** text input with answer-length validation
- **Multiple Choice:** single-choice controls

The practice page must not expose answer key or explanations before submission.

## Review Page Design

The review page must start with a score summary block:

- raw score (`correct / total`)
- estimated IELTS Band

Below the summary, questions are shown in review mode with:

- question type
- user answer
- correct answer
- correctness state
- evidence sentence
- paraphrase pairs
- explanation

Wrong and unanswered items should be visually emphasized. Correct items may be visually de-emphasized or collapsed by default.

The review page must preserve the spirit of the reading skill's post-submission analysis flow: score first, then evidence-based explanation, not answer dumping without reasoning.

The review page must also use the same shared UI shell so the transition from practice view to review view feels like one product, not two unrelated screens.

## Scoring and Result Model

### Score Outputs

The result page must show both:

1. **Raw score** — number correct out of total questions
2. **Estimated IELTS Band** — derived from the reading score conversion table

Because this first version only supports repository-generated original reading sets and the current design target is GT reading practice, the first version should use the **General Training reading conversion table** by default. If the reading-set configuration expands later to Academic mode, the Band conversion must become set-type aware.

Because the first-version practice set is shorter than a full official reading paper, the UI must label this number as an **estimated Band**, not an official score. The estimate should be derived by scaling the set score to a 40-question equivalent before applying the GT conversion table. This rule must be explicit in the implementation so every run uses the same estimation method.

### Per-Question Result Shape

Each question result must support at least:

- `questionId`
- `questionType`
- `userAnswer`
- `correctAnswer`
- `isCorrect`
- `evidence`
- `paraphrasePairs`
- `explanation`

## Data Flow

1. User invokes `ielts-reading`
2. Reading Skill Router determines whether the request matches the UI-supported training flow
3. For supported requests, Generator produces one original set
4. Set is written to project-local storage
5. Reading Skill Router launches the browser UI with a stable reference to the generated set
6. User answers questions and submits
7. Result Deriver computes raw score, Band estimate, and per-question results
8. Attempt result is written back to project-local storage
9. Browser navigates directly to the review page

If step 2 determines the request is not UI-supported, or the environment cannot launch the browser flow, the skill must continue with the terminal-based reading experience.

## Persistence

The first version should persist exactly three data groups:

1. generated reading set
2. submitted user answers
3. derived result and explanation payload

Persistence should follow the repository's existing local-project storage approach so CLI and browser flows can read the same project data later.

### UI Asset Persistence

The browser UI's shared visual layer must also live in the project as durable implementation assets.

That includes at least:

- shared page shell
- style tokens
- reusable component styles
- stable practice/review page structure

This is required so repeated `ielts-reading` UI launches are consistent because they reuse the same project-owned assets, not because the runtime tries to regenerate matching styles each time.

Runtime state should remain separate from these assets. Generated reading content, answers, and results are session data; the UI visual system is product code.

### Refresh Behavior

The first version should not autosave in-progress answers.

That means:

- refreshing before submission may discard unsaved answers
- refreshing after a successful submission should be able to reload the saved result view from persisted project data

This keeps the first version simple while still making completed attempts durable.

## Error Handling

- If reading-set generation fails or returns incomplete data, the browser must not enter the practice state.
- If answer submission cannot be persisted, the UI must report failure explicitly and must not pretend the attempt was saved.
- If result derivation fails, the UI must not navigate to the review page.
- Unanswered questions are allowed and must be represented explicitly as `unanswered`.

## Validation Rules

- T/F/NG and multiple-choice answers must be restricted to valid options.
- Sentence Completion answers must be checked against the question's word-limit rule.
- Submission is allowed with unanswered items.
- The review page must clearly differentiate wrong answers from unanswered items.

## Verification

The implementation plan must cover these checks:

1. a generated reading set renders completely in the practice page
2. submission produces the correct raw score
3. Band conversion uses the correct GT mapping
4. review page displays user answer, correct answer, evidence, and explanation correctly
5. persisted attempt data can be reloaded after refresh
6. repeated launches of UI-based reading training reuse the same visual shell and state styling
7. UI style consistency comes from project-persisted assets, not runtime-only generation
8. Band estimation uses one explicit and repeatable score-scaling rule for shortened practice sets

## Notes

This design is intentionally not a dashboard project. The first version is a focused training surface whose only job is to complete a stable flow from **practice** to **score** to **review** to **saved record**.
