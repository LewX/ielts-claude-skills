# v3.0 Core Design

**Date:** 2026-04-28  
**Status:** Approved for planning

## Problem

`ielts-claude-skills` today is a v1.0 prompt-only skill pack. It works well as a stateless coach, but it cannot deliver the README's v3.0 core value: cross-session history, structured mistake tracking, trend summaries, and project-scoped study state that survives across environments.

The current four `SKILL.md` files are still useful, but they only cover the interaction layer. They do not define a shared persistence model, a stable write path, or a way for multiple skills to contribute to one evolving study record.

## Goal

Deliver a **v3.0 core** architecture that keeps the existing skill experience but adds a lightweight local runtime and project-scoped persistent data.

This core version is intentionally narrower than the full README v3.0 vision:

- **In scope:** project-scoped persistence, history, findings, artifacts, trend summaries, writing-first rollout, reading second, shared use across Claude Code and Copilot CLI
- **Out of scope:** dashboard UI, status bar integration, cloud sync, a full application shell

## Product Direction

The system should evolve from a prompt-only repository into a **skills + lightweight local runtime** architecture.

The runtime is responsible for data validation, persistence, and derived summaries. The skills remain responsible for coaching behavior, routing, and user-facing outputs.

The persistent study state should live **inside the project**, not under `~/.ielts/`. The repository itself becomes the study workspace so users can carry the same history across machines and environments.

## Storage Location

All persistent data is stored under a project-local `.ielts/` directory and is **committed to git by default**.

```text
<repo>/.ielts/
  profile.json
  attempts/
  findings/
  artifacts/
  derived/
  backups/
```

### Rationale

- The project becomes the portable unit of study
- Claude Code and Copilot CLI can share one data directory naturally
- Users can move between environments by carrying the repository
- Backup and restore can be built on top of normal git workflows plus explicit archive tooling

### Trade-offs

- The repository now contains both prompts and study data
- Data written into git history must be curated, not raw transcript dumps
- Sensitive user text should be minimized in persisted records

## Core Data Model

The first version should use a deliberately small object model:

### 1. `profile`

Stores exam date, target band, current level snapshot, and user preferences. This is the context layer for planning and summary generation.

### 2. `attempt`

Represents one meaningful training event such as:

- one essay correction
- one reading review session
- one speaking artifact generation batch

An attempt stores timestamps, source skill, normalized scores, input metadata, and a compact summary of the result.

### 3. `finding`

Represents structured issues or observations extracted from attempts, such as:

- missed second prompt part
- article misuse
- false vs not given confusion
- weak transition use

Findings are the basis for error books, weak-area ranking, and recurring pattern analysis.

### 4. `artifact`

Represents reusable learning assets extracted or generated by the skills, such as:

- rewritten essay versions
- synonym pairs
- speaking story templates
- phrase banks

Artifacts let the system accumulate value across sessions without depending on chat history replay.

### 5. `study_plan`

Stores short-horizon recommended next steps derived from `profile`, recent attempts, and repeated findings. This is intentionally lightweight in the core version.

## Directory Structure

The runtime should organize persisted data like this:

```text
<repo>/.ielts/
  profile.json
  attempts/
    2026/
      writing-2026-04-28T09-00-00.json
      reading-2026-04-28T09-30-00.json
  findings/
    inbox.jsonl
  artifacts/
    synonyms.jsonl
    speaking-stories.jsonl
  derived/
    stats.json
    weak-spots.json
    next-step.json
  backups/
```

### Storage Format

The core version should start with **JSON and JSONL**, not SQLite.

Reasons:

- easy to inspect
- easy to diff and commit
- cross-platform without extra setup
- enough for the initial history and summary workload

If data volume or query complexity grows later, the runtime can migrate internally without changing the skill contract.

## Runtime and Skill Responsibilities

### Skills

Skills are responsible for:

- identifying the current coaching mode
- producing the user-facing explanation
- extracting structured output fields from the result
- deciding whether a session is worth persisting

### Runtime

The lightweight runtime is responsible for:

- schema validation
- file writes and updates
- rebuilding derived summaries
- backup and restore operations
- returning short summary payloads for skills to read

### Principle

**Skills should not directly edit project data files ad hoc.**  
They should interact through a small stable command surface owned by the runtime.

## Runtime Interface

Expose a minimal command surface, for example:

1. `ieltsctl init`  
   Initialize `.ielts/` and default files

2. `ieltsctl record`  
   Persist one normalized attempt and related findings or artifacts

3. `ieltsctl derive`  
   Recompute derived summaries and weak-area views

4. `ieltsctl summary`  
   Return project learning state for `/ielts`

5. `ieltsctl backup` / `ieltsctl restore`  
   Archive and recover project study data

This command surface is intentionally small so the skills stay stable even if storage internals change.

## How Existing Skills Change

The current `SKILL.md` files do not need a full rewrite. Their personalities, boundaries, and main modes remain valid. The primary changes are:

- add structured output expectations
- define persistence triggers
- align on shared tags and schemas

### `/ielts`

Current role: routing and basic coaching.

Core version role:

- read project summary state
- distinguish first-time use from returning use
- route based on both user intent and tracked weakness
- act as the study control layer, not just a router

### `/ielts-writing`

This is the first skill to connect to persistence.

It should emit:

- TR / CC / LR / GRA / overall
- normalized error tags
- attempt metadata
- rewritten output as an artifact
- mode distinction between prompt analysis and full correction

This skill becomes the primary data producer in phase 1.

### `/ielts-reading`

This is the second skill to connect.

It should emit:

- question type metadata
- mistake categories
- synonym pairs as artifacts
- grouped attempt records at passage or set level

This skill enables the error-book loop in phase 2.

### `/ielts-speaking`

This should initially emphasize artifact accumulation rather than score tracking.

It should emit:

- story templates
- upgraded expressions
- predicted Part 3 frames

Speaking trend scoring can wait until there is a stronger evaluation model.

## Persistence Policy

Not every conversation should be written to disk.

The runtime should persist only **meaningful study events**, such as:

- a completed essay review
- a completed reading mistake analysis
- a finalized speaking artifact batch
- a profile update

This avoids turning the repository into a raw transcript dump.

## Error Handling

The core version should be strict:

- invalid schema input rejects the write
- derived summary failures do not destroy previously valid derived files
- attempt data and derived data update independently
- user-facing output should explicitly say when analysis succeeded but archival failed

No silent fallback behavior should be introduced for invalid persisted data.

## Testing Strategy

The core version should cover:

- schema validation
- `record -> derive -> summary` flow
- project-local `.ielts/` initialization
- writing transformation into normalized attempt records
- reading transformation into normalized findings and artifacts

Tests should focus on preserving data integrity and stable contracts between skills and runtime.

## Delivery Phases

### Phase 1: Data Backbone

Deliver:

- `.ielts/` project initialization
- base schemas
- `ieltsctl init / record / derive / summary`
- `/ielts-writing` persistence
- `/ielts` summary-aware coaching

Outcome:

The project gains history, basic tagging, and trend-aware next-step guidance.

### Phase 2: Reading and Error Book Loop

Deliver:

- `/ielts-reading` persistence
- question-type level mistake tracking
- synonym accumulation
- weak-area ranking
- structured error-book outputs

Outcome:

The core promise of history + findings + trend guidance is complete.

### Phase 3: Expansion Layer

Deliver:

- `/ielts-listening`
- `/ielts-vocab`
- stronger `/ielts-speaking` artifact persistence
- backup and restore
- stable derived formats for future dashboard work

Outcome:

The system is ready to grow into the broader v3.0 product vision.

## Recommended MVP

If only one minimal but meaningful version is built first, it should include:

1. project-local `.ielts/`
2. lightweight `ieltsctl`
3. `/ielts-writing` persistence
4. `/ielts` reading derived summaries and recommending next actions

This is the smallest version that turns the project from "can answer" into "can accumulate, summarize, and guide".
